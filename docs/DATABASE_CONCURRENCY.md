# Параллельная работа с базой MarCat

SQLite допускает много одновременных читателей, но только одного писателя. Поэтому MarCat разделяет
«параллельность операций» и «параллельность физической записи»: пользовательские операции могут идти
одновременно, а их короткие записи в локальную базу выполняются по очереди.

## Координатор записи

- Все локальные подключения (`desktop`, MCP, фоновые воркеры, миграции) проходят через клиент из
  `@marcat/db`; отдельным подсистемам не нужно самостоятельно договариваться о блокировках.
- Перед изменяющим SQL клиент захватывает кооперативную блокировку рядом с файлом базы. Блокировка
  действует между процессами, а не только между промисами одного процесса.
- Транзакция удерживает блокировку целиком до `commit`, `rollback` или `close`. Обычный одиночный запрос
  освобождает её сразу после завершения.
- Чтения не захватывают блокировку и продолжают выполняться параллельно в режиме WAL.
- У блокировки есть владелец, назначение и heartbeat. После аварийного завершения процесса устаревшая
  блокировка восстанавливается автоматически; при превышении времени ожидания ошибка сообщает владельца.
- Небольшой retry остаётся последним уровнем защиты от внешнего процесса, который пишет в SQLite, не
  используя координатор MarCat.

Подключать локальную базу в обход `createDb` нельзя: такой писатель не участвует в общей очереди и снова
может вызвать `SQLITE_BUSY`.

## Долгие массовые операции

Долгая бизнес-операция не должна выполняться одной большой транзакцией. Массовое добавление авторов
создаёт устойчивую запись операции и отдельные элементы очереди, после чего сразу возвращает управление
интерфейсу или MCP.

Воркеры desktop и MCP берут операцию из очереди и обрабатывают каждый контакт коротким идемпотентным
шагом. Состояния и счётчики сохраняются после каждого элемента. Поэтому:

- интерфейс остаётся доступным, а прогресс виден после навигации и перезапуска;
- уже добавленные контакты не повторяются;
- отмена останавливает только оставшуюся часть;
- повтор запускает только неудачные элементы;
- после падения зависший элемент возвращается в очередь;
- одновременные воркеры безопасны: выбор следующей операции сериализован тем же координатором записи.

## Правила для новых операций

1. Разбивать работу на короткие идемпотентные элементы с устойчивым идентификатором.
2. Не держать транзакцию во время сетевого запроса, ожидания пользователя или обработки большого списка.
3. Не использовать `INSERT/UPDATE ... RETURNING` внутри транзакции, если результат можно получить явным
   идентификатором или отдельным `SELECT`: незавершённый statement способен заблокировать `commit`.
4. Давать операции назначение через `withDatabaseWritePurpose`, чтобы таймаут указывал виновника.
5. Проверять изменения межпроцессным тестом: один процесс удерживает транзакцию, второй ждёт и успешно
   продолжает; после аварийного выхода владельца блокировка должна восстановиться.
